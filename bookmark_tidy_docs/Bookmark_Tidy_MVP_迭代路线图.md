# Bookmark Tidy：3 天 MVP 迭代路线图

> 目标：在 2026-08-08 至 2026-08-10 三个日历日内交付一个可侧载、可演示、可安全试用的 v0.1，完成“扫描 → 建议 → 审阅 → 执行 → 撤销”的最小闭环。

| 项目项 | 计划 |
|---|---|
| 开发周期 | 3 个专注开发日（2026-08-08 至 2026-08-10） |
| 团队假设 | 1 名工程师，约 24 个有效工程小时 |
| 技术基线 | TypeScript、React、Vite、Chrome Manifest V3 |
| 发布方式 | 本地 `dist/` 侧载包，不提交 Chrome Web Store |
| 当前状态 | 工程骨架、Popup、Manager、Service Worker 和基础消息通道已完成 |
| 核心原则 | 分析不写入；所有写入先审阅；每个执行批次都可撤销 |

## 1. v0.1 交付范围

### 1.1 必须交付

- 读取 Chrome 书签树并转换为稳定的内部节点模型。
- Dashboard 展示书签数、文件夹数和问题数。
- 展示可搜索的扁平书签列表及完整路径。
- 归一化 URL，检测精确重复和安全的标准化重复。
- 检测空文件夹，排除根节点和 Chrome 受保护目录。
- 基于域名、标题关键词和现有文件夹名称生成最小分类建议。
- 在统一 Review 页面逐项选择或取消建议；删除建议默认不选中。
- 通过唯一的 Operation Engine 执行 `move` 和 `delete`。
- 在执行前保存快照，持久化最近一次批次，并支持撤销。
- 执行前重新验证节点；节点已变化时跳过并显示冲突。
- `typecheck`、`lint`、单元测试和生产构建全部通过。

### 1.2 明确延期到 v0.2+

- AI 分类、坏链检测、重定向检查和网页元数据抓取。
- 重命名、更新 URL、自动创建文件夹和文件夹合并。
- 多批次历史、复杂冲突恢复、重试队列和跨设备同步。
- 扫描进度、取消、后台定时任务和 Side Panel。
- 虚拟列表及 5,000 条以上书签库的专项性能优化。
- 完整视觉设计、国际化、无障碍专项和 Chrome Web Store 材料。
- 全量 E2E 自动化；v0.1 使用单元测试加人工安全验收。

> 三天版本不通过削弱安全约束来节省时间，只削减功能宽度和界面精细度。

## 2. 三天执行计划

### Day 1 — 只读扫描与确定性分析

**目标：** 用户可以扫描、浏览并看到可信的清理建议；全天不实现任何书签写入。

| ID | 工作项 | 预计 | 验收 |
|---|---|---:|---|
| D1-01 | 定义 `BookmarkNode`、扫描结果和索引类型 | 1h | 保存 id、类型、标题、URL、父级、索引、路径和日期 |
| D1-02 | 实现只读 Scanner 与扁平化 | 2h | 嵌套、空目录和特殊标题不报错；扫描模块无写 API |
| D1-03 | 实现 URL 归一化及回归测试 | 2h | 覆盖主机大小写、默认端口、尾斜杠、追踪参数和参数排序 |
| D1-04 | 实现重复项与空文件夹检测 | 1.5h | 输出稳定的 `Suggestion[]`，保护根目录 |
| D1-05 | 完成 Dashboard、搜索和问题列表 | 1.5h | 可按标题、URL、域名或路径过滤 |

**Day 1 Gate：** 扫描真实书签库时没有任何 `create`、`move`、`update` 或 `remove` 调用；刷新页面后可再次稳定扫描。

### Day 2 — 审阅、执行与撤销

**目标：** 打通最小安全写入闭环，并优先验证恢复能力。

| ID | 工作项 | 预计 | 验收 |
|---|---|---:|---|
| D2-01 | 定义 Suggestion、Operation、Batch 和 Snapshot | 1h | 覆盖移动、删除、结果和冲突状态 |
| D2-02 | 扩展 Bookmarks/Storage Adapter | 1.5h | 上层不直接调用 Chrome API；存储带 schema 版本 |
| D2-03 | 实现 Review 页面 | 1.5h | 显示 before/after、原因；删除默认不选中 |
| D2-04 | 实现预验证与 Operation Engine | 2h | 先验证后写入；逐项记录成功、失败和跳过 |
| D2-05 | 实现最近批次持久化与 Undo | 2h | 移动恢复位置；删除从快照重建并记录新 ID |

**Day 2 Gate：** 在专用测试文件夹执行“移动/删除 → 撤销”，数量、标题、URL、路径和可恢复的顺序与执行前一致。Gate 不通过时，Day 3 分类功能取消，优先修复撤销。

### Day 3 — 最小分类、集成与发布候选

**目标：** 加入产品差异化能力，完成端到端人工验收并产出侧载包。

| ID | 工作项 | 预计 | 验收 |
|---|---|---:|---|
| D3-01 | 提取现有文件夹特征并实现最小评分器 | 2h | 仅建议现有目录，返回置信度和命中原因 |
| D3-02 | 将分类移动接入统一 Review/Engine | 1.5h | 不建立第二套写入逻辑；低置信度默认不选中 |
| D3-03 | 错误、空状态和 Service Worker 重启处理 | 1.5h | 权限/API 失败有可恢复提示，不白屏 |
| D3-04 | 单元测试、人工安全脚本和缺陷修复 | 2h | 核心算法、消息协议、执行顺序和撤销均被验证 |
| D3-05 | 构建 v0.1 侧载包与使用说明 | 1h | `dist/` 可加载，Popup、Manager、Worker 无控制台错误 |

**Day 3 Gate：** 从新安装开始，完整完成扫描、清理建议、分类建议、审阅、执行和撤销；质量命令全部通过。

## 3. 数据与代码边界

```text
Chrome API
   ↓
Adapters（唯一 API 边界）
   ↓
Scanner → Analyzers → Suggestion[]
                         ↓
                      Review UI
                         ↓
                   Operation Engine
                    ↓             ↓
                Snapshots      Bookmarks Adapter
                    ↓
                  Undo
```

- `Scanner`、重复检测、空目录检测和分类评分器只能返回数据，不能导入执行模块。
- UI 只能发送版本化消息，不能直接调用 `chrome.bookmarks` 或 `chrome.storage`。
- 所有修改必须由 Service Worker 内的 Operation Engine 调用 adapter 完成。
- 删除前必须保存足以重建节点的快照；移动前必须保存 `parentId` 和 `index`。
- v0.1 只保留最近一次可撤销批次，以换取三天内可验证的实现规模。

## 4. v0.1 发布门槛

以下条件必须全部满足，才称为“三天 MVP 完成”：

- [ ] `npm run typecheck` 无错误。
- [ ] `npm run lint` 无错误或警告。
- [ ] `npm test` 全部通过。
- [ ] `npm run build` 成功并生成有效 Manifest V3 产物。
- [ ] Chrome 开发者模式可加载 `dist/`，Popup、Manager 和 Worker 无控制台错误。
- [ ] 只读扫描不修改书签。
- [ ] 重复项和空目录建议在相同输入下保持稳定。
- [ ] 删除操作默认不选中，所有写入前均有 Review。
- [ ] 并发修改节点会被识别为冲突并跳过。
- [ ] 专用测试文件夹的移动和删除可以撤销。
- [ ] 最近批次在 Manager 刷新和 Worker 重启后仍可撤销。

## 5. 时间不足时的降级顺序

严格按以下顺序缩减，不能削减快照、审阅、预验证或撤销：

1. 移除分类规则中的标题关键词，仅保留域名与现有文件夹匹配。
2. 移除路径搜索，只保留标题和 URL 搜索。
3. 移除标准化重复的自动建议，仅展示精确重复。
4. 移除 Dashboard 装饰性统计和视觉润色。
5. 如果 Day 2 Gate 仍未通过，只发布只读分析预览版，不开放写入按钮。

## 6. v0.1 完成后的首要工作

1. 将单批次撤销扩展为版本化历史和冲突恢复。
2. 增加大型书签库性能测试、扫描进度和取消。
3. 扩充分类规则、手动目标选择及新建目录审阅。
4. 完成无障碍、E2E、隐私说明和 Chrome Web Store 发布准备。

完整的 6 周设计任务仍保留在《MVP 开发任务清单》中，作为 v0.2 及后续版本的产品 backlog，不再作为 v0.1 的发布范围。
